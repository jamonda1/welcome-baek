# Java 실행 성능 개선

## 변경 내용

이전에는 테스트 케이스마다 자산 읽기, iframe/Worker 생성, JDK 압축 해제, WASM 모듈 컴파일, Java 소스 컴파일을 반복했습니다.

현재는 페이지에서 자산과 sandbox iframe을 유지합니다. JDK 압축 해제와 WASM 모듈 컴파일은 최초 준비 때 수행하며, Java 소스는 한 번 컴파일해 전체 케이스에 사용합니다. 마지막으로 컴파일에 성공한 소스가 같으면 다음 실행에서도 클래스 바이트코드를 재사용합니다. 입력이나 예상 출력 변경만으로 재컴파일하지 않습니다. 페이지 새로고침 시 이 메모리 캐시는 사라집니다. 코드나 실행 결과를 외부로 보내지 않습니다.

각 케이스는 새 Worker, WASM 인스턴스, 가상 파일시스템, JVM을 사용합니다. static 변수·시스템 속성·표준 입력과 출력이 다음 케이스로 넘어가지 않습니다. 컴파일 실패는 모든 케이스에 표시하고, 개별 실행 실패나 시간 초과 후에는 다음 케이스를 계속 실행합니다. 컴파일 제한 45초, 실행 환경 준비 제한 20초, VM 실행 단계 제한 5초를 적용합니다. VM 실행 제한에는 Java VM 초기화 비용도 포함되므로 백준 채점 시간과 직접 비교할 수 없습니다.

실행 중에는 컴파일/케이스 진행률, 편집 잠금과 로딩 아이콘을 표시합니다. 케이스 완료 즉시 결과를 갱신하고, 완료된 결과를 유지합니다.

## 측정 결과

2026-11-24 사용자 Windows PC, Node.js 24.18.0에서 실제 배포 WASM과 JDK를 사용해 A+B를 실행했습니다. 브라우저 Worker를 Node worker_threads로 연결한 측정이며, 설치된 Chrome 확장 프로그램의 전체 화면 동작을 측정한 값은 아닙니다. 디스크 자산 읽기는 측정 전에 수행했습니다. 각 구성 1회 측정으로 실행 환경에 따라 달라집니다.

| 조건 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 2개 케이스 최초 실행 | 21.53초 | 16.47초 |
| 동일 소스 2개 케이스 재실행 | 별도 측정 없음 | 5.81초 |
| 동일 소스 20개 케이스 재실행 | 별도 측정 없음 | 58.87초 |

최초 2개 케이스는 약 23.5% 단축됐습니다. 동일 소스 재실행은 기존 2개 케이스 측정값 대비 약 73% 단축됐습니다. 최초 실행의 Java 컴파일은 약 10.28초, 준비 작업은 약 0.18초였습니다. 재실행에서도 케이스당 약 2.9초가 필요합니다. 현재 인터프리터 기반 JVM의 초기화 비용이 남아 있어 20개 케이스가 즉시 끝나는 수준은 아닙니다.

추가 개선은 JVM 초기화 프로파일링, 클래스 로딩 개선, 런타임의 실행 방식 변경을 검토해야 합니다. Worker/JVM을 그대로 재사용하면 사용자 코드의 상태가 섞일 수 있으므로 격리 검증 없이 적용하면 안 됩니다. 병렬 실행도 메모리 사용과 UI 응답성 측정을 거쳐야 합니다.

원시 측정 기록은 [java-performance.json](java-performance.json), 런타임 검증 기록은 [java-runtime-verification.json](java-runtime-verification.json)에 있습니다.

## 재현

```powershell
npm run build
npm run typecheck
npm test
npm run test:java
npm run benchmark:java
```

`test:java`는 모의 런타임 없이 실제 Java를 실행해 내부 클래스/static 상태, 입력과 시스템 속성 격리, 시간 초과, 예외, System.exit, 문법 오류를 검사합니다. `benchmark:java`는 최초 2개, 동일 소스 2개, 동일 소스 20개를 순서대로 실행해 JSON 형식으로 시간을 출력합니다. 두 명령은 수십 초 이상 걸릴 수 있으며 속도 기준으로 통과/실패를 결정하지 않습니다. 자동 테스트 중 sandbox 테스트는 빌드된 번들을 읽으므로 먼저 빌드해야 합니다.

## Chrome 수동 확인

1. `chrome://extensions`에서 Welcome Baek을 새로고침하고 기존 백준 문제 탭도 새로고침합니다.
2. Java A+B 코드에 정상 입력 2개와 잘못된 예상 출력 1개를 등록하고 실행합니다.
3. 컴파일 중에는 모든 케이스가 대기 중이고 코드 편집/언어 전환이 잠기는지 확인합니다. 이후 케이스마다 실행 중 → 통과/실패로 갱신되고 마지막에 편집이 풀려야 합니다.
4. 같은 코드로 입력만 바꿔 다시 실행합니다. 첫 실행보다 빨라야 합니다. 소스를 바꾸면 재컴파일해야 합니다.
5. static 카운터를 증가시키는 코드를 여러 입력으로 실행해 매번 초기값부터 시작하는지 확인합니다. 무한 루프/예외 케이스 다음의 정상 케이스도 결과가 나와야 합니다.
6. 결과를 닫았다 다시 열어도 유지되는지, 자동 저장과 Ctrl+S, 언어/테마/레이아웃 복원이 유지되는지 확인합니다.
